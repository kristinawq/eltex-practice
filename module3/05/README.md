# Производитель-потребители: семафор + разделяемая память POSIX

## Сборка и запуск

```bash
make          # собрать ./prodcons
make test     # собрать и запустить Unity-тесты
make clean
```

Каждый процесс запускается в своём терминале. Первым запускается производитель, он
создаёт память и семафор:

```bash
./prodcons producer [размер_памяти]   # в байтах, от 64 до 65536, по умолчанию 1024
./prodcons consumer                   # можно запустить несколько
./prodcons clean                      # удалить память и семафор
```

Пока объекты существуют, их видно в `/dev/shm`: `pc_05_shm` и `sem.pc_05_sem`.

Пример вывода потребителя:

```
[consumer 163] набор: 62 94 32 8 42 -25 94 | max=94 min=-25
```

Заголовок `PcHeader` реализован как в 4 задании.

### Семафор

Именованный бинарный семафор POSIX `/pc_05_sem`: 1 - память свободна, 0 - занята.
Начальное значение 1 задаётся при создании в `sem_open`.

```c
sem_wait(sem);    /* занять: дождаться 1 и уменьшить до 0 */
sem_post(sem);    /* освободить: увеличить до 1 */
```

Это те же действия, что в задании 4 делали операции `lock = {0, -1, 0}` и `unlock`
через `semop`. Структуры `sembuf` у семафоров POSIX нет, ей соответствуют вызовы
`sem_wait` и `sem_post`.

Все обращения к списку (добавление блока, поиск необработанного набора, пометка
`count = 0`) выполняются между `sem_wait` и `sem_post`, поэтому два потребителя не могут
забрать один и тот же набор. Если `sem_wait` прерван сигналом (`EINTR`), вызов повторяется.

### Производитель

1. `pc_create`: `shm_open` с `O_EXCL` → `ftruncate` (задаёт размер) → `mmap` → заполнение
   заголовка → `sem_open` с `O_EXCL` и начальным значением 1. Семафор создаётся последним,
   поэтому потребитель не увидит память с неготовым заголовком.
2. Пока память не исчерпана: генерирует от 1 до 16 случайных чисел, записывает набор
   (`pc_put`), печатает его и засыпает на 0,3 с. Если очередной набор не поместился
   (`PC_FULL`), генерация заканчивается.
3. `pc_finish` ставит в заголовке `finished = 1`: потребители знают, что новых наборов не будет.
4. Пока `pc_unprocessed` возвращает больше нуля, производитель засыпает на 0,5 с и
   проверяет снова.
5. `pc_close(destroy)`: `munmap`, `close`, `sem_close`, затем `shm_unlink` и `sem_unlink`.

### Потребитель

1. `pc_open`: `sem_open` и `shm_open` без создания → `fstat` (узнать размер памяти) → `mmap`.
2. В цикле вызывает `pc_take`. Внутри, под блокировкой, она проходит по списку, находит
   первый набор с `count > 0`, копирует числа и ставит `count = 0`.
3. По полученным числам `main` находит максимум и минимум и печатает их.
4. После каждого шага засыпает на 0,7 с, в том числе когда необработанных наборов пока нет.
5. Завершается, когда `pc_take` вернул `PC_FINISHED` (производитель закончил, а
   необработанных наборов нет). Затем `munmap`, `close`, `sem_close`.

Если производитель успел вызвать `shm_unlink` и `sem_unlink`, потребитель продолжает
работать с уже открытыми объектами: имя удаляется сразу, а сам объект живёт, пока его кто-то
использует. Поэтому потребитель спокойно дочитывает всё и завершается штатно.

## Тесты

Unity-тесты (`make test`) проверяют библиотеку в одном процессе:

- формирование имён (`_shm`, `_sem`), отказ на пустом, `NULL` и слишком длинном имени;
- запись и чтение набора, пустой список, набор нельзя взять дважды;
- набор помечается `count = 0` и остаётся в списке;
- блоки связаны через `next`, у последнего `next = 0`, порядок сохраняется;
- переполнение памяти (`PC_FULL`), счётчик необработанных наборов;
- флаг «производитель закончил» (`PC_FINISHED`);
- два потребителя не получают один и тот же набор;
- слишком маленький буфер, неверные аргументы, повторное создание (`EEXIST`);
- удаление памяти и семафора после `pc_close(destroy)`, повторное удаление не считается ошибкой.
